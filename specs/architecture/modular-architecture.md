# PX-ARCH-001 — معماری ماژولار PredictX

- شناسه: `PX-ARCH-001`
- نسخه سند: 0.1
- وضعیت: پیشنهاد معماری برای بازبینی
- تاریخ: 2026-11-20
- دامنه: معماری منطقی و مرزهای مسئولیت؛ بدون تعهد به زبان یا زیرساخت نهایی

## 1. اهداف معماری

1. جلوگیری از نشت اطلاعات آینده در تمام مسیر پردازش.
2. قابلیت بازتولید هر نتیجه با نسخه داده، تعریف، کد و پارامترهای آزمایش.
3. جداسازی منطق پژوهش از فایل، پایگاه داده، API و رابط کاربری.
4. امکان جایگزینی منبع داده و فناوری ذخیره‌سازی بدون بازنویسی دامنه.
5. ساخت MVP با کمترین پیچیدگی عملیاتی و حفظ امکان توسعه.

## 2. سبک معماری پیشنهادی

برای نسخه نخست، **Modular Monolith با Pipelineهای مرحله‌ای** انتخاب می‌شود. ماژول‌ها در یک برنامه/مخزن کد و با قراردادهای روشن اجرا می‌شوند؛ مرز ماژول‌ها در سطح package و interface است، نه سرویس‌های شبکه‌ای مستقل.

Microservices، صف پیام، پردازش توزیع‌شده و معماری event-driven زیرساختی در MVP پیش‌فرض نیستند. فقط در صورت وجود شواهد اندازه‌گیری‌شده از نیاز به مقیاس، استقلال استقرار یا جداسازی بار کاری بررسی می‌شوند.

## 3. لایه‌های منطقی

### 3.1 Domain / Core
مفاهیم و قواعد خالص پژوهش:
- Candle و قرارداد زمان/قیمت
- Dataset و DatasetVersion
- DataQualityIssue و QualityReport
- FeatureDefinition و FeatureValue
- BehaviorDefinition، BehaviorOccurrence و BehaviorOutcome
- Experiment، ExperimentProtocol و EvaluationResult

این لایه نباید به فایل‌سیستم، دیتابیس، کتابخانه نمودار، API یا فریم‌ورک رابط کاربری وابسته باشد.

### 3.2 Application / Use Cases
هماهنگ‌کننده جریان‌های کاری:
- ImportMarketData
- ValidateDataset
- BuildFeatureSet
- DetectOccurrences
- CalculateOutcomes
- RunExperiment
- EvaluateExperiment
- GenerateResearchReport

Use caseها از قراردادهای ورودی/خروجی استفاده می‌کنند و منطق دامنه را اجرا/هماهنگ می‌کنند؛ جزئیات اتصال به ابزارها را در خود نگه نمی‌دارند.

### 3.3 Adapters / Infrastructure
پیاده‌سازی جزئیات بیرونی:
- آداپتور فایل و ارائه‌دهنده داده بازار
- ذخیره‌سازی داده و metadata
- محاسبه hash و ثبت provenance
- پیاده‌سازی موتورهای پردازش عددی/آماری
- ثبت log، تنظیمات و مدیریت خطا

هر آداپتور باید از طریق interface تعریف‌شده در لایه داخلی قابل تعویض باشد.

### 3.4 Interfaces
سطوح تعامل:
- CLI برای اجرای import، validation و experiment
- API در صورت نیاز مصرف‌کننده خارجی
- Dashboard برای مرور داده، آزمایش و نتایج

رابط کاربری صرفاً درخواست را ارسال و نتیجه را نمایش می‌دهد؛ نباید منطق detector، outcome یا اعتبارسنجی را دوباره پیاده‌سازی کند.

## 4. مرز ماژول‌ها و مسئولیت‌ها

| ماژول | مسئولیت | خروجی اصلی |
|---|---|---|
| ingestion | خواندن داده از منبع و ثبت مشخصات دریافت | RawBatch و SourceMetadata |
| market_data | تبدیل داده به قرارداد canonical بدون حذف نسخه خام | Candle و DatasetVersion |
| data_quality | بررسی schema، زمان، ترتیب، gap، duplicate و مقادیر نامعتبر | QualityReport |
| feature_engineering | ساخت ویژگی نسخه‌دار با زمان دسترسی مشخص | FeatureSet |
| temporal_analysis | استخراج ویژگی‌های تقویمی/جلسه‌ای با timezone معتبر | TemporalFeatureSet |
| behavior | تعریف نسخه‌دار و اجرای detector علّی | Occurrence |
| outcome | محاسبه پیامد پس از زمان وقوع و ثبت ناقص‌بودن | Outcome |
| discovery | جست‌وجوی توصیف‌ها/الگوهای کاندید و baselineها | CandidatePattern |
| validation | ارزیابی آماری، عدم‌قطعیت، وابستگی و multiple testing | ValidationResult |
| backtesting | شبیه‌سازی فرض‌های اجرا و هزینه‌ها، مستقل از detector | BacktestResult |
| experiments | ثبت پروتکل، نسخه‌ها، پارامترها و وضعیت اجرا | ExperimentRecord |
| reporting | ساخت گزارش قابل ممیزی از نتایج | ResearchReport |
| presentation | نمایش/تعامل با داده و نتایج | View Model / UI |

این جدول مرز مسئولیت است؛ الزاماً به معنی ساخت یک package یا سرویس جدا برای هر ردیف در MVP نیست. ماژول‌های کم‌حجم می‌توانند تا زمان رشد نیاز در یک package نزدیک باقی بمانند.

## 5. جریان داده استاندارد

1. **Raw ingestion:** داده دریافتی به‌صورت تغییرناپذیر یا قابل ردیابی نگهداری می‌شود؛ منبع، زمان دریافت، فایل/شناسه منبع و checksum ثبت می‌شوند.
2. **Canonicalization:** داده به schema استاندارد کندل تبدیل می‌شود؛ مقدار خام زمان و قرارداد timestamp منبع حفظ می‌شود.
3. **Quality gate:** خطاها و هشدارها محاسبه می‌شوند. داده فقط با سیاست پذیرش صریح وارد مراحل بعد می‌شود؛ اصلاح خودکار نباید بی‌ردپا باشد.
4. **Feature computation:** ویژگی‌ها با نسخه تعریف، پارامتر و `available_at` ساخته می‌شوند.
5. **Detection:** detector فقط داده/ویژگی قابل‌دسترس تا زمان تصمیم را می‌بیند و Occurrence مستقل تولید می‌کند.
6. **Outcome calculation:** outcome در مرحله جداگانه و از کندل بعدی طبق قرارداد PX-RS-001 محاسبه می‌شود.
7. **Discovery and validation:** الگوهای کاندید روی داده توسعه کشف و با پروتکل ازپیش‌ثبت‌شده اعتبارسنجی می‌شوند.
8. **Experiment/reporting:** ورودی‌ها، حذف‌ها، نسخه‌ها، نتایج و محدودیت‌ها به گزارش قابل بازتولید متصل می‌شوند.

هر مرحله باید شناسه ورودی و خروجی، نسخه قرارداد و وضعیت اجرا داشته باشد. اجرای مجدد با ورودی/نسخه یکسان باید رفتار idempotent یا خروجی قابل مقایسه داشته باشد.

## 6. قراردادهای کلیدی بین ماژول‌ها

- **MarketDataReader:** دریافت داده خام و metadata منبع؛ هیچ منطقه زمانی نامعلوم را UTC فرض نمی‌کند.
- **Canonicalizer:** تبدیل داده خام به کندل canonical همراه با mapping به رکورد منبع.
- **DatasetValidator:** ورودی DatasetVersion و سیاست کیفیت؛ خروجی گزارش خطا/هشدار و تصمیم پذیرش.
- **FeatureProvider:** دریافت DatasetVersion و FeatureDefinition؛ خروجی مقادیر به‌همراه زمان دسترسی، نسخه و provenance.
- **BehaviorDetector:** دریافت تعریف رفتار و ورودی‌های مجاز تا cutoff؛ خروجی Occurrence بدون دسترسی به outcome.
- **OutcomeCalculator:** دریافت Occurrence، داده بعد از وقوع و پروتکل outcome؛ خروجی Outcome یا وضعیت INCOMPLETE.
- **ExperimentRunner:** دریافت پروتکل immutable و dependencyهای نسخه‌دار؛ خروجی وضعیت اجرا و artifactها.
- **ReportBuilder:** دریافت نتایج و provenance؛ خروجی گزارش بدون تغییر نتایج اصلی.

قراردادها باید مستقل از فریم‌ورک باشند و schemaهای سریال‌سازی‌شده نسخه داشته باشند. جزئیات فیلدها در PX-DATA-001 تعیین می‌شوند.

## 7. جهت وابستگی

قاعده اصلی: وابستگی به سمت داخل است.

- Domain به هیچ لایه دیگری وابسته نیست.
- Application به Domain و interfaceهای تعریف‌شده در مرز داخلی وابسته است.
- Infrastructure، interfaceهای داخلی را پیاده‌سازی می‌کند؛ Domain نباید Infrastructure را import کند.
- Interfaces به Application متصل می‌شوند و فقط View Model مناسب ارائه می‌کنند.
- ماژول behavior نباید به outcome یا backtesting وابسته باشد.
- discovery و validation می‌توانند از خروجی‌های نسخه‌دار استفاده کنند، اما نباید داده آزمون نهایی را به چرخه کشف برگردانند.

## 8. نسخه‌بندی، provenance و بازتولید

هر Experiment حداقل باید ثبت کند:
- شناسه و نسخه protocol
- DatasetVersion و hash داده/manifest
- منبع، نماد، تایم‌فریم، واحد قیمت و قرارداد زمان
- نسخه BehaviorDefinition و FeatureDefinitionها
- commit کد و نسخه dependencyها
- پارامترها، seed و تنظیمات محاسباتی
- بازه‌های زمانی train/validation/test و روش walk-forward
- تعداد رکوردهای ورودی، پذیرفته‌شده، حذف‌شده و ناقص با علت
- نسخه schema و زمان اجرای pipeline

داده خام و artifactهای حجیم در Git ذخیره نمی‌شوند. Git برای کد، مستندات، schemaها و تنظیمات غیرمحرمانه است؛ محل نگهداری داده و artifact بعداً انتخاب می‌شود. credential فقط از secret manager یا متغیر محیطی امن دریافت می‌شود و هرگز در log یا commit قرار نمی‌گیرد.

## 9. تست و کنترل کیفیت

- **Unit:** قواعد domain، زمان، detector و outcome با ورودی‌های کوچک.
- **Contract:** سازگاری ورودی/خروجی آداپتورها و schemaهای نسخه‌دار.
- **Integration:** مسیر کامل ingest تا گزارش با داده fixture.
- **Golden tests:** خروجی‌های مرجع ثابت برای اطمینان از عدم تغییر ناخواسته.
- **Temporal/leakage tests:** تغییر داده آینده نباید detector یا featureهای زمان t را تغییر دهد؛ هیچ feature با `available_at` بعد از cutoff پذیرفته نشود.
- **Data-quality fixtures:** gap، duplicate، کندل ناقص، timestamp مبهم، DST و داده نامرتب.
- **Reproducibility tests:** اجرای یک آزمایش با ورودی و تنظیمات یکسان، نتیجه و metadata قابل مقایسه تولید کند.

## 10. خطا، مشاهده‌پذیری و امنیت

خطاها باید طبقه‌بندی شوند: خطای منبع، خطای schema، کیفیت داده، خطای محاسبه و خطای زیرساخت. هشدار کیفیت با خطای توقف pipeline یکی نیست و سیاست آن در سطح هر مرحله مشخص می‌شود.

Logها باید experiment_id، dataset_version و stage را حمل کنند، اما نباید credential یا داده حساس را ثبت کنند. مجوز استفاده و نگهداری داده بازار پیش از ingest واقعی باید بررسی شود.

## 11. سازگاری و مهاجرت

- schemaها دارای نسخه صریح هستند.
- تغییر ناسازگار با نسخه قبلی نیازمند migration مستند و تست است.
- artifactهای آزمایش قدیمی به نسخه schema و کد زمان تولید خود اشاره می‌کنند.
- داده و نتیجه تاریخی به‌صورت بی‌صدا بازنویسی نمی‌شوند؛ اصلاح، نسخه جدید و provenance جدید می‌سازد.

## 12. تصمیم‌های باز

موارد زیر عمداً در این مرحله نهایی نشده‌اند:
1. زبان و نسخه runtime
2. فرمت و محل ذخیره داده خام/canonical و metadata
3. منبع داده، مجوز و قرارداد timezone
4. موتور محاسباتی و کتابخانه‌های آماری
5. پایگاه داده یا نیاز به آن در MVP
6. ابزار orchestration و زمان‌بندی
7. چارچوب API و Dashboard
8. CI، بسته‌بندی و محیط استقرار

این موارد در PX-DATA-001 و مرحله انتخاب فناوری، با معیارهای حجم داده، تکرارپذیری، هزینه نگهداری، قابلیت تست و مهارت اجرایی ارزیابی می‌شوند.

## 13. معیار پذیرش معماری

- مرز detector و outcome در کد و قراردادها قابل اثبات باشد.
- هیچ وابستگی Domain به UI یا زیرساخت وجود نداشته باشد.
- هر خروجی پژوهشی به ورودی و نسخه‌های تولیدکننده قابل ردیابی باشد.
- مسیر pipeline با fixture قابل اجرا و تست باشد.
- آزمون خودکار برای نشت زمانی و داده ناقص وجود داشته باشد.
- هیچ فناوری یا فرض سودآوری بدون تصمیم و شواهد به‌عنوان الزام معماری ثبت نشده باشد.
